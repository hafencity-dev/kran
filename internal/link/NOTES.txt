internal/link notes for the lead (engineer E)
=============================================

Requests for internal/config (additive, optional)
-------------------------------------------------
None needed. link keeps its own per-peer state in
<ConfigDir>/links/<name>.json (peer's kran public key we authorized, the ssh
destination/args used, remote env overrides, tag) so Unlink can reverse exactly
what Link added. Nice-to-have: nothing else.

Hidden subcommands (cli wires them)
-----------------------------------
`kran internal <args...>` -> `link.InternalMain(args, os.Stdin, os.Stdout, os.Stderr)`
(args excludes "internal"; the first arg is link-info|link-accept|link-forget|link-probe;
other `kran internal …` verbs such as `supervise` stay with execenv).
Exit codes: 0 ok, 1 error (message on stderr), 2 usage. Output is one JSON object.

  link-info     -> Info JSON {id,name,os,arch,version,protocol,home,user,kran_path,
                   config_dir,state_dir,cache_dir,pubkey,host_key,addresses[],ssh_port,
                   has_daemon,binary_sha256}. Read-only. pubkey/id are "" before `kran setup`.
  link-accept   <- {"peer":PeerInfo,"tag":""}; ensures node id + key, adds the forced-command
                   authorized_keys line for peer.pubkey (command=<this kran> serve --stdio),
                   upserts peers.toml. -> Info + {"changed":bool}. Idempotent.
  link-forget   <- {"name","id","pubkey"}; removes that kran key line and the peer entry.
  link-probe    <- {"addresses":[],"host_key":"","user":""}; x/crypto/ssh handshake with the
                   local kran key; -> {ok_address,rtt_ms,results[]}.

Environment knob: KRAN_SSHD_HOSTKEY=<file> overrides /etc/ssh/ssh_host_ed25519_key.pub when
reporting this machine's sshd host key (tests, odd sshd setups).

What `kran setup --yes --quiet [--name N]` must guarantee (called remotely by Link)
-----------------------------------------------------------------------------------
Exit 0 and be idempotent; create dirs, node id (config.EnsureNodeID), kran key
(config.EnsureKey(name)), write config name when --name is given (only if not already set up with
another name), install + start the service. Silent with --quiet. It runs with KRAN_CONFIG_DIR/
KRAN_STATE_DIR/KRAN_RUNTIME_DIR/KRAN_CACHE_DIR exported when the link was made with RemoteEnv.
link does not need the daemon to run to finish linking; Info.has_daemon tells the CLI whether to
mention `kran service start`.

CLI wiring
----------
  link.Options: Host, Name, Version(internal/version.Version), SelfPath(os.Executable()),
    Interactive(tty), SSHArgs, Tag, RemoteEnv, RemoteBinDir, Progress(step,detail), Runner(nil=exec).
  Progress steps in order: connect, install (optional), setup (optional), keys, verify.
  link.Link(ctx, opts) (*Result, error); link.UnlinkDetailed(ctx, name, opts) (*UnlinkResult, error)
  link.Candidates(ctx, nil-or-link.ExecRunner{}) for the picker (arrow keys are the CLI's job;
  Candidate.Linked entries should be shown dimmed/last).
  Flags to expose: kran link [host] --name, --tag, --remote-env K=V (repeatable), --remote-bin-dir,
  -o/--ssh-arg passthrough; Result.Notes and Result.ReverseNote are printed as-is.

Behavior summary
----------------
* Control channel = system ssh, ControlMaster=auto ControlPersist=60, BatchMode=yes first; with a
  tty a failed attempt is retried once with the terminal attached (password / host key prompt).
* kran install on remote: same platform copies the running binary; others from the binary cache
  (paths.BinaryCache), gh release download, GitHub API with GITHUB_TOKEN/GH_TOKEN, or a source
  build (CGO_ENABLED=0 go build) - development versions try the source build first. Unchanged
  binaries (sha256) are never re-sent. macOS remotes also get the linux binary at
  <remote cache>/bin/<ver>/linux-<arch>/kran.
* Host key pinned: what the remote sshd reports over the authenticated channel, else known_hosts,
  else ssh-keyscan, else the key presented on the first verified handshake.
* Direction: both | outbound (we can dial them, they cannot dial us; ReverseNote explains) | inbound.
  peers.toml gets PreferredAddress (fastest) and, for dev setups, RemoteConfigDir and Tag.
* Tag: appended to the authorized_keys comment on both sides ("kran@<node> kran-dev").

Real-machine testing recipe (devmac = Mac Studio, Darwin arm64)
--------------------------------------------------------------
Not run by link's unit tests. Once the CLI is wired:

  export KRAN_CONFIG_DIR=/tmp/kran-e/cfg KRAN_STATE_DIR=/tmp/kran-e/state \
         KRAN_RUNTIME_DIR=/tmp/kran-e/run KRAN_CACHE_DIR=/tmp/kran-e/cache
  kran link devmac --tag kran-dev --remote-bin-dir '~/kran-dev/e/bin' \
     --remote-env KRAN_CONFIG_DIR='~/kran-dev/e/cfg' --remote-env KRAN_STATE_DIR='~/kran-dev/e/state' \
     --remote-env KRAN_RUNTIME_DIR='~/kran-dev/e/run'  --remote-env KRAN_CACHE_DIR='~/kran-dev/e/cache'
  (version "dev" cross-compiles darwin/arm64 from the checkout into $KRAN_CACHE_DIR automatically;
   the remote setup must not install the real launchd service: use the service instance derived from
   the KRAN_* env, see internal/service Options.Instance, or pass --no-service to setup if it exists.)

Cleanup (also what `kran unlink devmac` does):
  kran unlink devmac
  grep -n kran-dev ~/.ssh/authorized_keys            # locally: must be empty afterwards
  ssh devmac 'grep -n kran-dev ~/.ssh/authorized_keys; rm -rf ~/kran-dev/e'   # remote: must be empty
  ssh devmac 'launchctl list | grep -i kran'          # no dev agent left

Unfinished / caveats
--------------------
* Verified offline only (fake ssh that runs the remote script through a local `sh` with a separate
  HOME, plus in-process x/crypto/ssh servers). The first real run against devmac may expose ssh
  option/PATH surprises on macOS (non-interactive ssh has a minimal PATH; link only uses absolute
  paths and `sh -c`, `uname`, `cat`, `mv`, `sha256sum`/`shasum`).
* Windows remotes are rejected with a clear message.
* If the remote's sshd uses a non-ed25519 host key only, the pinned key comes from known_hosts or
  ssh-keyscan -t ed25519 may find nothing; the first verified handshake then pins what is presented.
